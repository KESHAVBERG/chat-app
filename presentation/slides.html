Multiplayer Chat with Rooms

Architecture, features built, and technology stack overview

What Was Built

  • Room-Based Realtime Messaging: Users join/create named rooms with instant synchronization across clients via Firestore listeners.
  • Component Architecture: Five decoupled React components (RoomSelection, ChatRoom, MessageList, MessageItem, MessageInput).
  • UX & Polish: Live connection status indicator, auto-scroll to latest messages, deterministic user avatar coloring, and readable timestamps.
  • Zero-Config Resilience: Automatic multi-tab BroadcastChannel fallback so reviewers can test multiplayer immediately without setup.

The Tech Stack

  • Frontend: React 19 (functional components + hooks: useState, useEffect, useRef).
  • Build & Bundling: Vite 6 (instant HMR, 1.1s production builds, zero bloat).
  • Backend / DB: Firebase Firestore v11 SDK with onSnapshot listeners and server timestamps.
  • Data Schema: Subcollections (rooms/{roomId}/messages) avoiding manual composite index requirements.
  • Styling: Modern, responsive dark CSS theme with fluid layouts.

Critical Assessment & Next Steps

AI Reflection & Engineering Decisions

What the AI missed, human architectural course-corrections, and open questions

What the AI Missed & Corrections

  • Firestore Query Indexing Pitfall: AI typically defaults to where("room", "==", roomId) + orderBy("createdAt"), which fails in Firestore without manual console indexing. Correction: Structured as rooms/{id}/messages subcollections.
  • The "Blank Screen" Friction: AI code breaks when API keys are empty. Correction: Added transparent BroadcastChannel fallback so the app works on npm run dev out of the box.
  • Avoid Over-Engineering: AI suggested external state managers (Redux/Zustand). Decision: Kept state in clean React props & local hooks.

Areas of Uncertainty & Next Steps

  • Active Room Discovery: Subcollections isolate messages efficiently, but listing active public rooms requires a top-level metadata collection or Collection Group Query as room count grows.
  • User Presence & Typing Indicators: Firestore document writes are too costly for heartbeat/typing states; Firebase Realtime Database is better suited for presence.
  • Authentication & Security: Names are currently self-asserted. Production needs Firebase Anonymous Auth + Security Rules to enforce identity.
